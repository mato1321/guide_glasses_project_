## 一句話版本

**「同一份程式碼，從手機搬到眼鏡，發現規格書上寫的東西有一半是假的。」**

前一天在小米手機上跑得好好的功能，換到 Rokid Glasses 上幾乎全部失效 ——
不是程式壞了，是**這台裝置宣告有、實際沒有**。整個過程可以概括成一句：
*不報錯，不代表成功。*

---

## 一、架構：沒有變

這是簡報裡值得強調的一點 —— **架構沒有改，只換了實作**。

```
app（組裝）
 └─ feature-assistant（流程）
     └─ core-domain（純 Kotlin，零 Android 相依，333 個測試在這裡）
         ↑ 由 glasses/* 與 ai/* 提供實作
```

`core-domain` 只套用 `kotlin.jvm`，任何 `android.*` 的 import 都會**編譯失敗** ——
這是建置層面強制的約束。好處在這次搬遷中完全兌現：

| 換掉的東西 | 改動範圍 |
|---|---|
| Android TTS → 自帶 VITS 模型 | 一個 DI 綁定 |
| Android STT → 自帶 zipformer | 一個 DI 綁定 |
| 喚醒詞 → 關鍵詞偵測 | 一個 DI 綁定 |

**上層邏輯與 333 個測試一行都沒改。**

## 二、小米手機（前一天）vs Rokid Glasses（今天）

| | 小米手機 | Rokid Glasses |
|---|---|---|
| 系統 | Android | YodaOS（Android 12） |
| CPU | 8 核，中高階 | **4 核 @2.0GHz** |
| RAM | 6–12 GB | **1.8 GB** |
| 電池 | 4000mAh+ | **210mAh** |
| Google Play Services | 有 | ❌ **沒有**（連 Play Store 都沒有） |
| 語音辨識服務 | 有 | ❌ **一個都沒有** |
| Android TTS 框架 | 有 | ❌ **整層被拿掉**（204 個系統服務裡沒有任何語音相關） |
| GPS | 有 | ❌ 宣告有、無 provider |
| 電子羅盤 | 有 | ❌ 沒有 |
| 前鏡頭 | 有 | ❌ 宣告有、實際沒有 |
| 相機擷取 | ~100ms | **930ms** |
| 背景執行 | 正常 | ❌ **預設每個 App 都被背景限制** |

### 這造成什麼

前一天在手機上，語音是「呼叫系統 API，50ms 完成」。
今天在眼鏡上，**那些 API 全部不存在**。

---

## 三、解法：把引擎當函式庫，繞開整層框架

關鍵洞察是一句話：**「綁不上 TTS」不等於「不能出聲」。**

眼鏡的音訊輸出本身是好的，壞的只有 Android 的 TTS 框架那一層。
所以不去修框架，而是整個繞過：

```
文字 → VITS (ONNX 推論) → PCM → AudioTrack → 喇叭      ← 完全不碰 TextToSpeech
麥克風 → AudioRecord → zipformer (ONNX) → 文字         ← 完全不碰 SpeechRecognizer
麥克風 → AudioRecord → 關鍵詞偵測 → 直接執行指令        ← 連轉文字都不需要
```

APK 從 106 MB 變成 288 MB —— 那是把整套語音能力搬進裝置的代價。

## 四、實測數字（可以直接放上投影片）

| 指標 | 數字 |
|---|---:|
| 語音指令偵測模型 | 4.6 MB，載入 2.5 秒 |
| 中文語音合成 | 22050Hz，RTF 約 1.5 |
| 快取命中的播報 | 額外開銷 **73ms** |
| OCR 全程 | 約 3 秒 |
| 人臉同步 | 2 人 6 張照片，一次成功 |
| 前景服務效果 | `oom adj` 905（會被殺）→ **200**（存活） |
| 單元測試 | **333 個，全過**（純 JVM，秒級） |

## 五、七次「靜默失敗」—— 簡報的高潮在這裡

這是整個過程最值得講的部分，因為它不是技術細節，是**方法論**。

| # | 什麼東西 | 表面現象 | 真相 |
|---|---|---|---|
| 1 | Rokid `bindSecurityService` | 不拋例外 | 永遠不回呼，5 秒後 `isReady()` 仍為 false |
| 2 | `pm list features` | 宣告有前鏡頭、GPS | 都沒有 |
| 3 | `startForeground()` | 沒有例外 | 被系統靜默拒絕，行程仍是 cached |
| 4 | `VOICE_RECOGNITION` 音訊來源 | 錄音「成功」 | **收到的全是 0**，只有這一種來源是啞的 |
| 5 | `adb install` | 回報 `Success` | 裝置上還是舊版（106 MB vs 288 MB） |
| 6 | TTS「載入中」 | 被判定為「不可用」 | 開機前 12 秒所有播報被默默丟掉 |
| 7 | 自己寫的防重入檢查 | 邏輯看起來對 | 講完一次指令後喚醒監聽再也回不來 |

**結論一句話：任何 API 呼叫「沒有拋例外」都不等於成功。**

對策也是一句話：**主動查證**。量麥克風音量、查 `isForeground` 旗標、
核對 APK 大小、加逾時檢查 —— 每一項都是被這七次逼出來的。

## 六、還沒解決的（誠實的一頁）

| 問題 | 現況 |
|---|---|
| 沒有台灣腔中文語音 | sherpa-onnx 的中文模型**全部是 zh-CN**，換模型解決不了 |
| 運算慢 | 4 核 2GHz 的硬限制。OCR 3 秒、TTS RTF 1.5 |
| 障礙物播報達不到 300ms 安全預算 | 只有走快取才達得到 |
| 導航 | 無 GPS **且**無電子羅盤，連「往左轉還往右轉」都算不出來 |
| 背景限制要靠 adb 解除 | 量產需要 Device Owner 或 MDM |

### 下一步的取捨（可以放在簡報最後當討論題）

**把 OCR／翻譯／人臉的運算卸載到手機會快很多**，因為：

- 音訊與文字的資料量很小（麥克風 32 KB/秒），Wi-Fi 往返只多 50–150ms
- 瓶頸純粹是 CPU，而手機快 3–10 倍

但**視覺不該卸載**（影像大，相機又在眼鏡上），而且**障礙物警示不能依賴手機** ——
手機沒帶、沒電、斷線就等於使用者失去安全功能。

## 七、給簡報生成工具的 prompt

把這份文件連同下面這段一起給 AI，可以產出投影片草稿：

```text
請根據附上的 docs/PRESENTATION.md 產出一份 12–15 頁的專題進度簡報（繁體中文）。

對象：資訊系老師與同學，聽得懂技術名詞但不熟 Android 內部。
語氣：工程實錄，不要行銷腔。數字一律標「實測」。

結構：
1. 封面：Rokid AI 導盲眼鏡 —— 從手機到眼鏡的移植實錄
2. 專案是什麼、要解決誰的問題
3. 前一天：小米手機上跑通了什麼
4. 今天：換到眼鏡上，哪些東西當場失效（用對照表）
5. 關鍵洞察：「綁不上 TTS」不等於「不能出聲」
6. 解法：把引擎當函式庫，繞開整層框架（用那三行資料流圖）
7. 架構沒有改，只換了實作（強調 core-domain 的零 Android 相依）
8. 實測數字
9. 🔴 重點頁：七次「靜默失敗」的對照表
10. 從中學到的方法論：不報錯 ≠ 成功，要主動查證
11. 還沒解決的問題（誠實列出）
12. 下一步的取捨：要不要把運算卸載到手機

要求：
- 每頁講一件事，字少、圖或表為主
- 第 9 頁是高潮，給它最多空間
- 不要美化，「還沒解決」那頁要保留
```

## 八、可以放進簡報的原始佐證

需要截圖或引用 log 時，這些是最有說服力的：

**音訊來源探針**（唯一沒接的剛好是最該用的那個）
```
VOICE_RECOGNITION：0.0000  ← 靜音
MIC：              0.0387
CAMCORDER：        0.0439
```

**前景服務被靜默拒絕**
```
W ActivityManager: Service.startForeground() not allowed due to bg restriction
```

**辨識正確但指令不匹配**（繁簡問題）
```
I OfflineAsr: 辨識完成：「前面有什么」
I OfflineTts: 快取命中「我還不會回答這種問題⋯」
```

**喚醒詞四個音節全被聽壞**
```
呼 → 胡、哭、不    叫 → 照、啸    盲 → 忙、芒、猛    狗 → 够
```

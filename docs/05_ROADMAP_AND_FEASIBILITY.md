## 1. Roadmap

> 時間估算基準：**1–2 位全職開發者**。若是課餘專題團隊，請把工時乘以 2.5–3。

## 2. 可行性分析（誠實版）

> 你要求「不要因為我要做就全部說可以」。以下是我認為必須直說的部分。

### 2.1 整體判定

| 功能 | 可行性 | 判定 |
|---|---|---|
| 三、AI 助理 | 🟢 **高** | 技術成熟，是整個專案最穩的部分 |
| 六、OCR | 🟢 **高** | ML Kit 成熟，現有程式碼品質好 |
| 五、語音/翻譯 | 🟢 **高** | Android 原生即可 |
| 二、人臉辨識 | 🟡 **中高** | 技術可行；**法遵與隱私是主要風險，非技術風險** |
| 一、障礙物偵測 | 🟠 **中** | **取決於相機串流能否解決**（Phase 0 V3）。且「導盲磚／斑馬線」需自行標註訓練 |
| 四、智慧導航 | 🟠 **中低** | 步行部分可行；**公車「哪一輛車進站」是尚未解決的難題** |

### 2.2 必須正視的硬限制

#### 🔴 限制 1：眼鏡沒有公開的連續影像串流 API

**這是全案最大的技術風險。**

我查遍官方文件與社群資料，CXR-M 只找到 `takeGlassPhoto()` 單張拍照。社群專案 RokidStream 自行實作串流，實測只有 **240×240 @ 10fps @ 100kbps（BLE L2CAP）** —— 這個解析度對物件偵測**幾乎不可用**（YOLO 通常需要 640×640）。

**替代方案：**
- Wi-Fi Direct 通道（`initWifiP2P()`）頻寬應該足夠，但**需要眼鏡端配合的 App**（CXR-S），而這需要 Rokid 開發者資格
- **最保險的 fallback：手機相機掛在胸前。** 體驗打折，但功能完整
- 或者接受「查詢式」定位：使用者停下來按鍵問「前面有什麼」

**建議：Phase 0 就把這件事問清楚（直接聯繫 Rokid 技術支援），不要等到 Phase 4 才發現。**

#### 🔴 限制 2：續航

眼鏡 **210 mAh / 4 小時**（不開相機）。導盲眼鏡的使用情境是「出門一整天」。

**這不是可以靠優化解決的問題，是物理限制。**

**必須接受的產品定位：**
- 眼鏡只在「需要時」開啟感測（事件驅動）
- 行動電源盒（3000 mAh，10 次充電）是**標配而非配件**
- 或者：長時間外出時改用手機相機模式

#### 🔴 限制 3：Android 前景服務限制

Android 14+ 對前景服務、背景定位、背景相機有嚴格限制：
- 相機在背景（螢幕關閉）**無法使用**，除非 App 在前景
- 需要 `FOREGROUND_SERVICE_LOCATION` 型別宣告 + 執行時使用者可見通知
- 部分廠商（小米、OPPO、華為）的省電機制會**主動殺掉**長時間執行的服務

**後果：** 使用者不能把手機放進口袋鎖螢幕就走。需要「螢幕常亮但變暗」的模式，這又進一步耗電。
**必須實測目標裝置的廠商 ROM 行為。**

#### 🔴 限制 4：「哪一輛公車進站」

TDX 告訴你「307 還有 1 分鐘」，但站牌可能同時停靠 8 條路線的車。**視障者看不到車頭號碼。**

這是**產品層面尚未有可靠解法的問題**：
- OCR 辨識車頭路線號碼：技術可行，但公車進站時在移動、角度多變、可能被人擋住 —— **成功率我不敢保證超過 70%**
- 引導使用者向司機出聲詢問：可靠，但依賴社會互動
- 藍牙信標：需要公車業者配合，不在你能控制的範圍

**建議：不要承諾自動上車。** 設計成「輔助 + 確認」：系統說「307 應該快到了，請向司機確認」，並提供 OCR 輔助作為額外參考。

#### 🟠 限制 5：延遲鏈

即使每一段都優化，端到端延遲仍是：

```
拍照(?ms) → 傳輸(?ms) → 推論(40ms) → 後處理(10ms) → TTS(50ms) → 眼鏡播報(?ms)
```

三個 `?` 都要 Phase 0 實測。**若總和 >500ms，「行進中即時警示」的價值會大打折扣** —— 以正常步行速度 1.4 m/s 計算，500ms 就是 0.7 公尺。

#### 🟠 限制 6：訓練資料

導盲磚、斑馬線、臺灣的路障樣式 —— **COCO 沒有，開源資料集也很少臺灣本地的**。

需要：實地錄製 2000–5000 張 → 標註 → 訓練 → 驗證。**這是 2–4 週的純資料工作**，沒有捷徑（GroundingDINO 自動標註能省時間，但仍需人工修正）。

#### 🟠 限制 7：成本

以 100 位使用者、每天使用 2 小時估算：

| 項目 | 月成本估算 |
|---|---|
| LLM（Haiku 4.5，每人每天 50 次查詢） | ~US$30–60 |
| Google Maps（Directions + Places） | ~US$100–200 |
| Cloud Vision（OCR fallback 10%） | ~US$15 |
| Cloud Run | ~US$20 |
| TDX | 免費（有配額限制） |
| **合計** | **~US$165–295/月** |

**Google Maps 是最大宗。** 必須做積極的快取與節流。
若不收費，這是需要長期補助的營運成本。**這是產品可持續性的問題，建議及早規劃。**

#### 🟡 限制 8：人臉辨識的法律風險

在公共場所辨識未同意的人臉，在臺灣涉及《個人資料保護法》。即使資料只存在本機：
- 建議**限制在「使用者主動註冊過的人」**，不做主動掃描陌生人
- 提供清楚的隱私政策
- 若要商業化，建議諮詢法律意見

### 2.3 我建議的取捨

如果資源有限，我會這樣排優先級：

| 優先 | 功能 | 理由 |
|---|---|---|
| 1 | **AI 助理 + OCR** | 技術風險最低、對視障者日常價值最高（看藥袋、看菜單、看信件是每天都會遇到的） |
| 2 | **人臉辨識** | 高情感價值（「知道走過來的是誰」），技術可控 |
| 3 | **步行導航（5a）** | 價值高，技術風險中等 |
| 4 | **障礙物偵測** | 價值最高但風險最高，且**現有導盲杖已能處理近距離障礙** —— 系統的增量價值主要在「杖子碰不到的」（頭部高度、遠距離接近的車輛） |
| 5 | **公車整合（5b）** | 價值高但「哪一輛車」問題未解 |

**特別說明第 4 項：** 導盲杖已經非常有效地處理地面障礙。**這套系統的差異化不應該是「取代導盲杖」，而是「提供杖子給不了的資訊」** —— 遠距離接近的車輛、頭部高度的障礙、環境的語意描述、人的身分。這個定位差異會改變功能一的設計方向。

### 2.4 最後的誠實建議

**這個專案的技術規劃是合理的，但目前的程式碼與目標之間的落差比表面上看起來大。**

具體來說：
- 現在有的是 **5 個各自獨立的原型**，不是 1 個系統的 5 個模組
- Rokid SDK **一行都還沒真正用上**
- 最關鍵的架構問題（相機串流、續航、播報仲裁）**都還沒被觸碰**
- 兩把正式金鑰**已經外洩**

**但好消息是：** 你已經證明了每個功能的「核心演算法」是可行的（InsightFace 能認人、Vision 能讀字、YOLO 能偵測）。剩下的是**工程整合問題，不是研究問題**。這比反過來要好得多。

**我的建議：不要在現有 5 個專案上修修補補。** 建立新的多模組專案，把有價值的資產（`splitTextForSpeech`、播報冷卻、人臉資料、提示音檔）移植過去，其餘重寫。**改造成本會高於重寫成本。**
